# 模块诊断功能（HookStatus）说明

> 对应代码：`app/src/main/java/io/github/imroxy2222/lsp_colorOSRecord/HookStatus.kt`。
> 用户入口：录音列表右上角菜单 → **模块设置**（第 4 个自定义菜单项，itemId `0x1A2B3C50`）。

## 一、这个功能是什么

一个**纯代码构建的浮动诊断面板**（Dialog，白底自绘，不依赖宿主任何资源/主题），
集中展示：

1. **环境信息**：录音 APP 版本、模块 versionCode、Android 版本；
2. **功能状态**：生成摘要开关、转文本队列进度、摘要队列状态；
3. **Hook 点定位状态**：模块依赖的每一个 hook/反射目标的定位结果。

定位动机：模块强依赖宿主（ColorOS 录音机）的类名与方法签名，宿主升级后符号
可能漂移导致功能静默失效。有了这个面板，**用户截图（或点"复制全部"）发给维护者，
即可立刻判断是宿主哪个版本改了哪个符号、该更新哪个定位锚点**，无需来回猜。

## 二、状态语义

每个 hook 点是一个 `HookStatus.Entry`，状态机为：

| 状态 | 面板显示 | 颜色 | 含义 |
| --- | --- | --- | --- |
| `PENDING` | 定位中 | 蓝 `#1565C0` | 尚未定位（DexKit 后台跑着 / 菜单尚未 inflate / 摘要懒解析未触发） |
| `FOUND` | 已找到 | 绿 `#1B7E3C` | 定位并 hook 成功（detail 里注明层1 / DexKit / 运行时 + 实际类名） |
| `NOT_FOUND` | 未找到 | 红 `#C62828` | 定位失败，对应功能失效 |
| `OPTIONAL_MISSING` | 可选·缺 | 橙 `#E65100` | 可选加固点未找到（功能可用，缺防重等辅助能力） |
| `DISABLED` | 已停用 | 灰 `#757575` | 因依赖缺失被主动停用 |

**特别注意 `PENDING`**：面板打开时如果还停在"定位中"，不一定异常——

- `summary_pipe`（摘要管道）是**懒解析**的，只有第一次真正要生成摘要、
  或用户打开诊断面板时（`showPanel` 会调 `SummaryQueue.prefetchResolveAsync()`）
  才会触发解析。打开面板后等几秒，面板会**每 2.5s 自动刷新**（最多 5 次），
  状态会自己变过来；
- `menu_items` 要等列表页菜单**第一次展开**才上报（运行时才能知道注入是否成功）。

## 四、如何新增：给新 hook 点接入诊断

**原则：每注册一个新 hook/反射目标，就必须同步接入状态上报。**
上报是成对的——成功路径 `found()`，失败路径 `missing()`（或 `optionalMissing()`）。
历史上 `menu_click` 只写了失败分支漏了成功分支，导致面板永远显示"定位中"，
排查半天发现不是 hook 失效而是漏报——**新代码务必两条路径都写**。

### 步骤 1：在 `HookStatus.init {}` 里注册条目

```kotlin
init {
    // ...
    // 新功能：XXX
    register("my_new_hook", "新功能·干什么的", "预期类#方法签名")
}
```

- `id`：全局唯一短标识（snake_case），后续上报都用它；
- `feature`：**给人看的**，写清这个点支撑什么功能（失效时用户看这个就知道影响面）；
- `target`：预期的 `类#方法` 签名，按 17.8.8 已知形态写。

### 步骤 2：在定位代码的成功/失败路径上报

```kotlin
private fun installMyNewHook() {
    val method = try {
        Class.forName(CLS_XXX, false, cl).getDeclaredMethod("foo", Long::class.javaPrimitiveType)
    } catch (t: Throwable) {
        XLog.w("MyNewHook not found: ${t.message}")
        HookStatus.missing("my_new_hook", "定位失败: ${t.message}（功能影响描述）")
        return
    }
    api.hook(method)
        .setExceptionMode(XposedInterface.ExceptionMode.PROTECTIVE)
        .intercept { /* ... */ }
    // 成功路径别漏！
    HookStatus.found("my_new_hook", "层1", "实际: ${method.declaringClass.name}")
    XLog.i("hooked ${method.declaringClass.name}#foo [my-new-hook]")
}
```

### 可选增强

- **DexKit 兜底分层上报**：层1 失败走 DexKit 时，各层分别报，`layer` 参数写
  `"层1"` / `"DexKit"`（参考 `trigger`、`search_dao`、`summary_pipe` 的写法）；
- **可选加固点**：缺了不影响主功能的（如防重检测），失败用
  `HookStatus.optionalMissing(id, "缺了以后的行为描述")`，面板显示橙色"可选·缺"；
- **运行时状态**：不是"定位"而是"运行中才知道"的状态（如菜单项是否真注入了），
  在实际发生的代码路径上报，`layer` 写 `"运行时"`（参考 `menu_items`）；
- **新功能要显示队列/开关状态**：在 `renderContent` 的"功能状态"区块加一行，
  数据源对象上提供 `statusText(): String`（参考 `ConvertQueue` / `SummaryQueue`）。

### 上报 API 一览

```kotlin
HookStatus.found(id, layer, detail = null)          // 已找到
HookStatus.missing(id, detail = null)               // 未找到（功能失效）
HookStatus.optionalMissing(id, detail = null)       // 可选点缺失（功能可用）
HookStatus.disabled(id, detail = null)              // 主动停用
```

上报线程不限（内部有锁），面板渲染在主线程。

## 五、如何用诊断信息 debug

### 面板排查流程

1. **先看环境信息**：宿主版本变了没有？符号漂移基本都发生在宿主升级之后；
2. **再看功能状态**：开关/队列状态能排除"配置问题"（如摘要开关被关了）；
3. **逐条看 Hook 点状态**：
   - 绿色 → 该链路定位正常；
   - 橙色"可选·缺" → 主功能不受影响，忽略或后续加固；
   - 蓝色"定位中" → 先等自动刷新；`summary_pipe` 长期不动则点"刷新"手动触发解析；
   - 红色"未找到" → 看 `实际:` 后面的失败原因，这就是要修的锚点。
4. **点"复制全部"**：整个状态导出为纯文本进剪贴板，比截图精确，可直接贴进 issue。

### "未找到"之后怎么修

以 `search_bind`（`xg.b#D()`）为例：

1. 拿新版本宿主 APK 重新反编译（jadx）；
2. 用面板里的 `target` 和失败原因定位旧符号的下落：类名/方法名被 R8 重排了，
   但**日志字符串、SQL 常量、内联资源 id 这些锚点通常还在**——全局 grep 锚点
   字符串找到新类，再看类内结构确定新方法名；
3. 更新代码里的已知名常量（层1），若锚点本身也变了，同步改 DexKit 匹配器
   （参考 `SummaryDexKitResolver.kt` / `DexKitResolver.kt`）；
4. 重装后用面板确认变绿。

### LSPosed 日志关键词（面板之外的第二手信息）

在 LSPosed 管理器日志（按模块过滤）里搜：

| 关键词 | 能看到什么 |
| --- | --- |
| `lsp_colorOSRecord` / `module loaded` | 模块是否加载、加载进了哪个进程 |
| `hooked` | 每个 hook 点安装成功的记录 |
| `not found` / `unresolved` | 定位失败的点（与面板"未找到"对应） |
| `dexkit` | DexKit 兜底定位过程与结果 |
| `summary engine` | 摘要管道层1/DexKit 解析结果 |

### "复制全部"导出格式

```
=== 录音增强模块状态 ===
录音APP: 17.8.8(17008008)
模块versionCode: 1 / Android 16
生成摘要开关: 开
转文本队列: 空闲
摘要队列: 空闲
[OK] 菜单项注入（hook 入口） | 目标: COUIToolbar#inflateMenu(int) | 定位: 层1 | 实际: ...
[缺失] 搜索注入·标签修正（摘要→转文本） | 目标: xg.b#D() | ...
```

`[OK]/[缺失]/[可选缺失]/[停用]/[定位中]` 与面板五种状态一一对应。

## 六、实现注意事项（改 UI 前先读）

- **纯代码构建，零宿主资源**：Dialog、布局、颜色、背景全部代码自绘。宿主主题
  变化不影响面板，也不要图省事去 `R.layout` / `R.color` 引宿主资源；
- **按钮**：彩色圆角胶囊 = `GradientDrawable` + `StateListDrawable`（按压加深 15%），
  `stateListAnimator = null` 去 Material 投影，`minWidth = 0` 去系统 88dp 最小宽；
- **自动刷新**：面板打开时有 `PENDING` 条目则每 2.5s 重渲染，最多 5 次，
  渲染前先 `removeCallbacks` 防泄漏；
- **懒解析触发**：`showPanel` 会调 `SummaryQueue.prefetchResolveAsync()`，
  让平时不触发的摘要管道解析也在面板上可见；
- **模块版本反查**：模块跑在宿主进程里，宿主 `PackageManager` 不认识模块包名，
  所以用 `ModuleMain` 捕获的模块自身 `ApplicationInfo` + `getPackageArchiveInfo`
  反查版本（`ModuleInfo`）；
- **异常兜底**：`showPanel` 整体 try-catch，面板崩了只 toast，绝不影响宿主。
